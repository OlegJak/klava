# 0001. Данные в Supabase — одна таблица «ключ — значение»

Дата: 2026-10-02 · Статус: принято

## Контекст

Спецификация (#1) предполагала в Supabase отдельные таблицы для папок, модулей, карточек, прогресса и настроек.
К моменту подключения Supabase (#12, #13) ядро обучения (`core.js`) уже работает через подключаемое хранилище
с синхронным интерфейсом `get(key) / set(key, value)` и держит данные в нескольких JSON-записях:
`own` (свои папки, модули и карточки), `progress` (коробки Лейтнера), `hidden`, `recent` и настройки.
Пользователь один — владелец сайта.

## Решение

В Supabase одна таблица `kv (user_id, key, value jsonb, updated_at)` с политиками «только владелец».
Хранилище Supabase для ядра — те же ключи: при входе все записи читаются в память, ядро работает с памятью
синхронно, каждая запись `set` сразу уходит в Supabase. Схема — [`supabase/schema.sql`](../../supabase/schema.sql).

## Последствия

- Ядро и его тесты не меняются; хранилище Supabase — ещё одна реализация того же интерфейса.
- Изменение одной карточки переписывает всю запись `own` (десятки–сотни КБ) — для одного человека приемлемо.
- Одновременная правка с двух устройств: последняя запись ключа побеждает целиком. Для одного человека это редкость;
  если станет проблемой — разбить `own` на записи по модулям, не меняя схему.
- Смотреть данные в панели Supabase менее удобно: они в JSON.
